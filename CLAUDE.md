## Project state

This is a personal account-transfer API project, built to support a backend developer job application. The owner has to be able to explain every line in an interview, so keep the code simple and explicit. Explain the design reasoning for each new file in Korean. Base package: `com.kyongseo.banktransfer`.

The work is staged:
- Stage 1: basic API with no concurrency control.
- Stage 2: reproduced lost updates from concurrent transfers.
- Stage 3: fixed them with pessimistic locking.
- Stage 4: added optimistic locking with retry next to the pessimistic version. Both stay in the code so they can be compared.
- Stage 5: compared the two with k6.
- Stage 6 (current): added `Idempotency-Key` support.

**Keep both implementations. Don't change the locking strategy or isolation level unless asked.**

## Architecture

The code is organized by feature package:
- `account`: `Account` entity, repository, service, controller and DTOs. The balance is a `long` in KRW. It changes only through `deposit`/`withdraw`, which enforce positive amounts and no overdraft. API lookups use `accountNumber` (a random 12-digit string generated by the server), never the DB id.
- `transfer`: `TransferService` is a non-transactional facade. It dispatches on `LockStrategy` (`PESSIMISTIC` | `OPTIMISTIC`). The strategy comes from the `?lockStrategy=` query param on `POST /api/transfers`, or else from `bank.transfer.lock-strategy` (bound to the `TransferProperties` record). Each implementation owns its transaction boundary.
  - `PessimisticLockTransferService` (one `@Transactional` unit):
    1. It resolves both ids with an id-only projection (`findIdByAccountNumber`, no lock).
    2. It locks both rows with `findByIdForUpdate` (`PESSIMISTIC_WRITE` → `SELECT ... FOR UPDATE`), **always in ascending id order regardless of transfer direction**. This prevents deadlocks.
    3. It calls withdraw and deposit; dirty checking persists the changes (no explicit `save`).

    Step 1 must stay id-only: loading the full `Account` before locking would leave a stale balance in the persistence context, and the later `FOR UPDATE` would not refresh it.
  - `OptimisticLockTransferService` relies on `Account.@Version`.
    - Each attempt runs in a **new** transaction through `TransactionTemplate`. Don't use `@Transactional` here: a retry inside the same transaction or persistence context would keep conflicting, and self-invocation would bypass the proxy.
    - It retries only on `OptimisticLockingFailureException`, up to `bank.transfer.optimistic.max-attempts`, with a jittered backoff. When all attempts fail it throws `TRANSFER_CONFLICT` (409). Business errors such as insufficient balance are not retried.
    - Deadlocks in this path are prevented by `hibernate.order_updates: true`, which sorts flush UPDATEs by PK.
  - `TransferMetrics` counts optimistic retries and conflict failures for the comparison tests.
- `idempotency` (stage 6): the optional `Idempotency-Key` header on `POST /api/transfers` is stored in MySQL (`idempotency_record`), deliberately not Redis, so the key commits atomically with the transfer. Flow (`TransferService` → `IdempotencyService`):
  1. `findReplay`: if the key is COMPLETED, return the stored response without transferring. The controller then sets `Idempotent-Replayed: true`.
  2. `prepare`: a short separate transaction runs `INSERT ... ON DUPLICATE KEY UPDATE id = id` and leaves a PENDING row.
  3. Inside each implementation's transfer transaction, `lock` runs `SELECT ... FOR UPDATE` on the key row **before** the account locks. If the row is already COMPLETED, it replays; otherwise it transfers and `complete` marks the row COMPLETED in the same commit.

  Don't move the key INSERT into the transfer transaction. When the first transaction rolls back (e.g. insufficient balance), waiting duplicate-key INSERTs deadlock on S→X lock upgrades; this was reproduced in stage 6. Same key with a different body → `IDEMPOTENCY_KEY_REUSED` (409). A failed transfer leaves the row PENDING, so the same key can be retried. There is no TTL cleanup and no per-client key scoping yet.
- `global/exception`: `BusinessException` (unchecked, so it triggers rollback) carries an `ErrorCode` enum that holds the HTTP status and message. `GlobalExceptionHandler` turns these and bean-validation errors into `ErrorResponse{code, message}`.

Unit tests use Mockito and need no DB:
- `PessimisticLockTransferServiceTest` covers business rules and verifies the id lock order with `InOrder`.
- `OptimisticLockTransferServiceTest` mocks `TransactionTemplate` to script conflicts and covers the retry policy.

The concurrency tests run against the real MySQL. Each is an `@EnumSource(LockStrategy)` parameterized test, and it prints success/failure counts, retries, expected vs. actual balances and elapsed time:
- `TransferConcurrencyTest`: 100 concurrent 1,000 KRW transfers from A (100,000) to B.
- `TransferDeadlockTest`: 50 A→B and 50 B→A transfers at once.
- `TransferIdempotencyTest`: 10 concurrent requests with the same key must produce exactly 1 transfer and 9 replays. It also covers the case where the first request fails with no deadlock, sequential replay, and key reuse with a different body.

Both tests assert that the balances match the **successful** transfer count (no lost updates). Only `PESSIMISTIC` must also succeed on all 100; `OPTIMISTIC` may fail with `TRANSFER_CONFLICT` once retries run out. These test classes must not be `@Transactional`, because each transfer has to commit in its own transaction for the race to happen. To override the retry limit, set an env var, for example `BANK_TRANSFER_OPTIMISTIC_MAXATTEMPTS=30 ./gradlew test ...`.

## Load testing (k6)

`k6/` holds the k6 comparison of the two locking strategies (stage 5). `k6/README.md` has the commands and the measured results.
- `k6/run-all.sh` runs two scenarios (`hot` = one sender, `spread` = 1,000 random accounts) × both strategies.
- `reset.sql` recreates only the `K6%` accounts.
- `verify.py` checks the MySQL balances and the version sum against k6's success count.

Start the app with `--spring.profiles.active=loadtest`, which turns SQL logging off. Results go to `k6/results/` (gitignored). Snap-installed k6 can't write outside `$HOME`. Only put numbers that were actually measured into the results tables.


## Local infrastructure notes

- `application.yml` points at `localhost` MySQL (`bank` DB, user `bank`/`bank1234`, `serverTimezone=Asia/Seoul`) and Redis. The credentials match `docker-compose.yml`.
- `@SpringBootTest` tests load the full context, so they need MySQL and Redis running (`docker compose up -d`). No test profile, H2, or Testcontainers is set up.
- Kafka is a dependency, but `docker-compose.yml` has no broker and there is no `spring.kafka` config yet. Add both before writing Kafka producers or consumers.
- JPA uses `ddl-auto: update` (Hibernate manages the schema; there are no migration scripts), `open-in-view: false` (load lazy associations inside the service/transaction layer), and `show-sql` is on.
