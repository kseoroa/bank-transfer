# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This is a personal account-transfer API project, built to support a backend developer job application. The owner has to be able to explain every line in an interview, so keep the code simple and explicit. Explain the design reasoning for each new file in Korean. Base package: `com.kyongseo.banktransfer`.

The work is staged. Stage 1 (done) has no concurrency control. Stage 2 will first reproduce lost updates from concurrent transfers and only then fix them. **Don't add locks, `@Version` or isolation changes unless asked.**

## Architecture

The code is organized by feature package:
- `account`: `Account` entity, repository, service, controller and DTOs. The balance is a `long` in KRW. It changes only through `deposit`/`withdraw`, which enforce positive amounts and no overdraft. API lookups use `accountNumber` (a random 12-digit string generated by the server), never the DB id.
- `transfer`: `TransferService.transfer(from, to, amount)` runs as one `@Transactional` unit. It reads both accounts, then calls withdraw and deposit, and dirty checking persists the changes (there is no explicit `save`). This read-modify-write path is where the stage 2 race condition will be reproduced.
- `global/exception`: `BusinessException` (unchecked, so it triggers rollback) carries an `ErrorCode` enum that holds the HTTP status and message. `GlobalExceptionHandler` turns these and bean-validation errors into `ErrorResponse{code, message}`.

Unit tests use Mockito with a mocked `AccountRepository` and need no DB (for example `TransferServiceTest`).

`TransferConcurrencyTest` (stage 2) runs 100 concurrent 1,000 KRW transfers from A (100,000) to B against the real MySQL. It asserts the correct result (A=0, B=100,000), so **it fails on purpose until stage 3 adds concurrency control**, and a full `./gradlew test` fails with it. The test class must not be `@Transactional`, because each transfer has to commit in its own transaction for the race to happen.

## Stack

- Java 21 (Gradle toolchain), Spring Boot 4.2, Gradle 9 wrapper
- Spring Web MVC, Data JPA (MySQL), Data Redis, Kafka, Validation, Lombok

## Commands

```bash
docker compose up -d                 # start MySQL 8 (bank-mysql :3306) and Redis 7 (bank-redis :6379)
./gradlew bootRun                    # run the app on :8080
./gradlew build                      # compile + test
./gradlew test                       # all tests
./gradlew test --tests 'com.kyongseo.banktransfer.SomeTest'            # single class
./gradlew test --tests 'com.kyongseo.banktransfer.SomeTest.methodName' # single method
```

## Local infrastructure notes

- `application.yml` points at `localhost` MySQL (`bank` DB, user `bank`/`bank1234`, `serverTimezone=Asia/Seoul`) and Redis. The credentials match `docker-compose.yml`.
- `@SpringBootTest` tests load the full context, so they need MySQL and Redis running (`docker compose up -d`). No test profile, H2, or Testcontainers is set up.
- Kafka is a dependency, but `docker-compose.yml` has no broker and there is no `spring.kafka` config yet. Add both before writing Kafka producers or consumers.
- JPA uses `ddl-auto: update` (Hibernate manages the schema; there are no migration scripts), `open-in-view: false` (load lazy associations inside the service/transaction layer), and `show-sql` is on.
