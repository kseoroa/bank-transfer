# 단계별 작업 기록 (1~6단계)

> 이 문서는 "그때 무엇을 했고, 왜 그렇게 했는지"를 쉽게 따라가려고 만들었다.
> 숫자는 모두 실제 테스트에서 나온 값이다.
> 동시성 개념을 더 깊게 정리한 문서는 [concurrency.md](concurrency.md)를 보면 된다.

## 한눈에 보기

| 단계 | 한 일 | 한 줄 요약 |
|---|---|---|
| 1 | 계좌 생성·조회·이체 API | 일단 "보통의" 이체를 만든다. 일부러 락은 넣지 않는다 |
| 2 | 동시 이체 문제 재현 | 100건을 동시에 보냈더니 **10건만** 반영됐다 |
| 3 | 비관적 락 | "먼저 잠그고 처리" → 100건 모두 정확. 양방향 이체의 데드락도 해결 |
| 4 | 낙관적 락 | "일단 처리하고 저장할 때 확인" → 정확하지만 몰리는 상황에서는 절반이 실패 |
| 5 | k6 부하 테스트 | 실제 HTTP 부하로 두 방식을 비교 |
| 6 | 중복 요청 방지 | 같은 요청이 10번 와도 이체는 **1번** |

## 1단계: 기본 이체 API

### 무엇을 했나
- `Account` 엔티티(id, 계좌번호, 소유자 이름, 잔액)를 만들었다.
- 계좌 생성, 잔액 조회, A → B 이체 API를 만들었다.
- 잔액이 부족하면 `INSUFFICIENT_BALANCE`(409) 에러를 돌려준다.
- 이체 서비스 단위 테스트를 작성했다.

### 왜 이렇게 했나
| 결정 | 이유 |
|---|---|
| 잔액을 `long`(원 단위)으로 | 원화는 소수점이 없다. `double`은 계산 오차가 생겨서 돈에 쓰면 안 된다 |
| setter 없이 `deposit()`/`withdraw()`만 둠 | 잔액을 바꾸는 길을 두 개로 막아 두면 "잔액은 음수가 될 수 없다"는 규칙을 엔티티가 직접 지킨다 |
| API는 DB id가 아니라 계좌번호로 조회 | 1, 2, 3처럼 증가하는 id를 노출하면 남의 계좌를 추측하기 쉽다 |
| 예외는 `BusinessException` + `ErrorCode` 하나로 | 에러 종류가 늘어도 enum에 한 줄만 추가하면 된다. unchecked 예외라 `@Transactional`이 자동으로 롤백한다 |
| **락을 일부러 안 넣음** | 다음 단계에서 "락이 없으면 무슨 일이 생기는지" 먼저 눈으로 보기 위해서 |

### 그때 실행한 명령과 이유
| 명령 | 이유 |
|---|---|
| `sh ./gradlew test --tests '...TransferServiceTest'` | `./gradlew`에 실행 권한이 없어서 `Permission denied`가 나서 `sh`로 실행했다. 전체 테스트 중 `contextLoads`는 MySQL이 필요해서 단위 테스트만 돌렸다 |

**결과**: 단위 테스트 9건 통과.

## 2단계: 동시 이체 문제 재현

### 비유로 먼저
화이트보드에 "잔액 100,000"이 적혀 있다. 두 사람이 동시에 그걸 보고, 각자 머릿속으로 1,000을 빼서 "99,000"으로 고쳐 쓴다.
두 번 뺐으니 98,000이어야 하는데 보드에는 99,000이 남는다. **한 사람의 작업이 덮어써져 사라졌다.** 이것을 **lost update**라고 한다.

### 무엇을 했나
A 계좌(100,000원)에서 B로 1,000원씩 **100건을 동시에** 보내는 테스트를 만들었다. 실제 MySQL에서 돌렸다.

| | 기대값 | 실제값 |
|---|---:|---:|
| A 잔액 | 0 | **90,000** |
| B 잔액 | 100,000 | **10,000** |

100건 모두 "성공" 응답을 받았지만 실제로는 10건만 반영됐다. 3번 돌려서 3번 다 같았다.

### 왜 이렇게 했나
| 결정 | 이유 |
|---|---|
| Mockito가 아니라 **실제 MySQL**로 | 이 문제는 DB의 트랜잭션·락 동작에서 생긴다. 가짜 DB로는 재현되지 않는다 |
| 테스트에 `@Transactional`을 안 붙임 | 붙이면 100건이 테스트의 한 트랜잭션 안에서 돌아서 경쟁 자체가 일어나지 않는다 |
| `CountDownLatch`로 동시에 출발 | 스레드를 준비시킨 뒤 신호 한 번에 출발시켜야 실제로 겹친다 |
| 단언은 **올바른 값(A=0)** 으로 둠 | 지금은 테스트가 실패하는 게 "재현 성공"이다. 3단계에서 고치면 같은 테스트가 그대로 통과해야 한다 |

### 그때 실행한 명령과 이유
| 명령 | 이유 |
|---|---|
| `docker compose ps` | 테스트 전에 MySQL이 떠 있는지 확인 |
| `build.gradle`에 `testLogging { showStandardStreams = true }` 추가 | Gradle은 테스트의 출력(System.out)을 기본으로 숨긴다. 기대값/실제값 표를 터미널에서 보려고 켰다 |
| 같은 테스트를 2번 더 실행 | 한 번 우연히 틀린 건지, 항상 틀리는 건지 확인 |
| `SPRING_DATASOURCE_HIKARI_MAXIMUMPOOLSIZE=5`로 다시 실행 | "정확히 10건인 건 커넥션 풀이 10개라서"라는 추측을 확인하려고. 풀을 5로 줄였더니 **20건**(A 80,000원)이 반영돼서 추측이 맞았다 |

### 기억할 점
- MySQL 기본 격리 수준(REPEATABLE READ)도 이 문제를 막지 못한다. 일반 SELECT는 락을 걸지 않기 때문이다.
- 이 경우 A+B 합계는 100,000원으로 맞았다. **총액 검사로는 잡히지 않는 버그**다.

## 3단계: 비관적 락

### 비유로 먼저
**화장실 열쇠.** 들어가는 사람이 문을 잠그고, 다음 사람은 밖에서 기다린다. 동시에 들어갈 수 없으니 덮어쓸 일도 없다.
SQL로는 `SELECT ... FOR UPDATE`(읽으면서 잠그기)다.

### 무엇을 했나
1. **먼저 단순하게**: 보내는 계좌 → 받는 계좌 순서로 잠갔다. 100건 테스트가 통과했다(A 0원 / B 100,000원).
2. **양방향 테스트 추가**: A→B 50건과 B→A 50건을 동시에 보냈더니 **데드락**이 났다. 100건 중 51건, 50건이 실패했다(2회 실행).
3. **해결**: 방향과 상관없이 **계좌 id가 작은 쪽부터** 잠그게 바꿨다. 3회 모두 100건이 성공했다.

### 데드락 비유
좁은 골목에서 차 두 대가 마주 보고 "네가 먼저 비켜"라며 서로 기다리는 상황이다.
- T1(A→B): A를 잠그고 B를 기다림
- T2(B→A): B를 잠그고 A를 기다림 → 영원히 못 감

**해결 규칙**: "모두 번호가 작은 계좌부터 잠근다." 그러면 둘 다 A부터 잡으려 하고, 한쪽이 먼저 잡으면 다른 쪽은 그냥 줄을 서게 된다. 마주 보는 상황이 생기지 않는다.

### 왜 이렇게 했나
| 결정 | 이유 |
|---|---|
| 일부러 단순한 순서로 먼저 구현 | 데드락이 정말 생기는지 눈으로 보고, 해결 전후를 비교하려고 |
| id를 먼저 조회할 때 **id만** 가져옴 | 계좌 전체를 먼저 읽으면 JPA가 그 오래된 잔액을 기억해 두고, 나중에 잠그면서 다시 읽어도 기억해 둔 값을 쓴다. 그러면 락을 걸어도 lost update가 다시 생긴다 |
| 락 순서를 단위 테스트(`InOrder`)로 고정 | 통합 테스트는 데드락이 "확률적으로" 나지만, 단위 테스트는 "항상 id 1 → 2 순서"라는 규칙 자체를 매번 확인한다 |

### 그때 실행한 명령과 이유
| 명령 | 이유 |
|---|---|
| 락을 넣기 전에 2단계 테스트를 3번 실행해서 시간 측정 | 락을 넣으면 얼마나 느려지는지 비교할 기준값(1,087~1,158ms)이 필요했다 |
| 단순 버전으로 양방향 테스트를 2번 실행 | 데드락이 한 번만 우연히 난 게 아님을 확인 |
| 결과 출력을 `grep`으로 걸러서 다시 실행 | 데드락 경고 로그가 너무 많아서 결과 표가 화면 밖으로 밀려났다 |

## 4단계: 낙관적 락

### 비유로 먼저
**위키 문서 편집.** 잠그지 않고 각자 편집하다가, 저장할 때 "내가 열었던 뒤에 누가 먼저 저장했나?"를 확인한다. 누가 먼저 저장했으면 내 저장은 실패하고 처음부터 다시 한다.
JPA에서는 `@Version` 숫자로 확인한다(저장할 때마다 1씩 증가).

### 무엇을 했나
- `Account`에 `@Version`을 추가했다.
- 충돌이 나면 최대 5번까지 다시 시도하고, 그래도 안 되면 `TRANSFER_CONFLICT`(409)로 실패시킨다.
- 비관적 락 코드는 그대로 두고, `?lockStrategy=OPTIMISTIC`처럼 요청마다 방식을 고를 수 있게 했다.

**같은 조건(100건 동시)으로 비교한 결과**:

| 방식 | 성공 | 실패 | 재시도 | 걸린 시간 |
|---|---:|---:|---:|---|
| 비관적 락 | 100 | 0 | 0 | 1,677~1,805ms |
| 낙관적 락 (5번 시도) | 44~45 | 55~56 | 308~313 | 1,361~1,450ms |
| 낙관적 락 (100번 시도) | 100 | 0 | 800 | 3,290ms |

두 방식 모두 **성공한 이체는 하나도 유실되지 않았다.** 낙관적 락의 실패는 돈이 사라진 게 아니라 "이체 거절"이다.

### 왜 이렇게 했나
| 결정 | 이유 |
|---|---|
| 재시도할 때마다 **새 트랜잭션** (`TransactionTemplate`) | 같은 트랜잭션에서 다시 하면 JPA가 기억해 둔 오래된 값 때문에 계속 충돌한다 |
| 재시도 전에 무작위로 잠깐 대기(jitter) | 충돌한 요청들이 똑같은 시간을 기다렸다 다시 오면 또 함께 충돌한다 |
| 잔액 부족은 재시도 안 함 | 다시 해도 결과가 같다 |
| 방식을 쿼리 파라미터로 선택 | 다음 단계에서 k6로 서버를 재시작하지 않고 두 방식을 번갈아 테스트하려고 |
| 재시도 횟수 바꿔 보기(5 → 30 → 100) | 횟수를 늘리면 성공은 늘지만 얼마나 느려지는지 보려고 |

### 그때 실행한 명령과 이유
| 명령 | 이유 |
|---|---|
| `git mv TransferService.java PessimisticLockTransferService.java` | 파일 이름을 바꿔도 git 이력이 이어지게 하려고. ⚠️ 이 이름 변경만 먼저 커밋되면서 커밋 `6748e63`은 컴파일되지 않는 상태가 됐다(파일 이름과 클래스 이름이 다름). 다음 커밋에서 고쳤다 |
| `BANK_TRANSFER_OPTIMISTIC_MAXATTEMPTS=30`, `=100` 환경변수로 테스트 | 코드를 고치지 않고 설정값만 바꿔 실험하려고 |
| 앱을 **18080** 포트로 띄워 `curl` 호출 | 8080은 IntelliJ에서 띄운 예전 버전 앱이 쓰고 있었다. 직접 띄운 게 아니라서 종료하지 않고 포트를 피했다 |

## 5단계: k6 부하 테스트

### 비유로 먼저
**가짜 손님 50명**이 30초 동안 쉬지 않고 이체 버튼을 누른다. 그동안 초당 몇 건이 성공했는지, 응답이 얼마나 걸렸는지 잰다.

### 무엇을 했나
- 시나리오 2개 × 방식 2개 = 4가지 조합을 3번씩 돌렸다.
  - **hot**: 한 계좌에서 100개 계좌로 보냄 (한 줄에 손님이 몰림)
  - **spread**: 1,000개 계좌끼리 무작위로 보냄 (손님이 흩어짐)
- 끝나면 MySQL에서 실제 잔액을 읽어 k6가 센 성공 건수와 맞는지 검사했다. 12번 모두 일치했다.

| 시나리오 | 비관적 락 성공 TPS | 낙관적 락 성공 TPS | 낙관적 락 실패율 |
|---|---|---|---|
| hot (3회) | 54.0 / 31.5 / 45.8 | 38.5 / 21.7 / 34.2 | 58.1% / 59.9% / 58.6% |
| spread (3회) | 192.4 / 157.0 / 283.6 | 207.0 / 220.6 / 267.8 | 0% |

- **hot**: 3번 모두 비관적 락이 이겼다.
- **spread**: 회차마다 이긴 쪽이 달라서 **어느 쪽이 빠르다고 말할 수 없다.** 측정 편차가 방식 간 차이보다 컸다.

### 왜 이렇게 했나
| 결정 | 이유 |
|---|---|
| 테스트 계좌를 SQL로 만듦 (`K6`로 시작) | API로 1,100개를 만들면 느리고, 계좌번호가 랜덤이라 스크립트가 알 수 없다. `K6`로 시작하는 계좌만 지워서 다른 데이터는 안전하다 |
| "성공 TPS"를 따로 셈 | 낙관적 락은 실패 응답이 빨리 오기 때문에 전체 TPS만 보면 실제보다 좋아 보인다 |
| 잔액 검증에 version 합계도 사용 | 이체 1건이 성공하면 두 계좌의 version이 1씩 오른다. 그래서 "성공 응답 수 = 실제 커밋 수"를 확인할 수 있다 |
| SQL 로그를 끄는 `loadtest` 프로필 | 켜 두면 DB 속도가 아니라 콘솔 출력 속도를 재게 된다 |
| 시작 전 워밍업 10초 | 앱을 막 띄운 직후는 느려서(JIT 컴파일), 처음 돈 조합만 불리해진다 |

### 그때 실행한 명령과 이유
| 명령 | 이유 |
|---|---|
| 5초짜리 짧은 실행 먼저 | 30초 × 4번을 돌리기 전에 스크립트, 검증, 표 출력이 다 되는지 빠르게 확인 |
| 결과 폴더를 `/tmp` → 프로젝트 안으로 | snap으로 설치한 k6는 홈 폴더 밖에 파일을 못 쓴다. 실제로 실패해서 알게 됐고, `run.sh`에 안내 메시지를 넣었다 |
| 전체를 **3번** 실행 | 2회차가 1회차보다 크게 느려서(54.0 → 31.5 TPS), 2번만으로는 결론을 낼 수 없었다 |
| `uptime` | 측정 중 장비가 얼마나 바빴는지 기록하려고 (load average 5~7) |

## 6단계: 중복 요청 방지 (Idempotency-Key)

### 비유로 먼저
**영수증 번호.** 손님이 "주문번호 abc로 이체해 주세요"라고 하면, 같은 번호로 다시 와도 "그건 이미 처리했어요. 여기 그때 영수증이요"라고 돌려준다.
네트워크가 끊겨서 앱이 같은 요청을 다시 보내도 돈이 두 번 나가지 않게 하려는 것이다.

### 무엇을 했나
- 요청 헤더 `Idempotency-Key`를 받는다.
- 같은 키의 두 번째 요청부터는 이체하지 않고 첫 결과를 돌려준다(응답 헤더 `Idempotent-Replayed: true`).
- 같은 키에 내용이 다르면 거절한다(`IDEMPOTENCY_KEY_REUSED`).

| 테스트 (두 락 방식 모두, 3회) | 결과 |
|---|---|
| 같은 키로 10건 동시 요청 | 이체 1건 + 재전송 9건, 10건 모두 같은 응답, A 99,000원 / B 1,000원 |
| 같은 키 10건, 첫 요청이 잔액 부족 | 10건 모두 `INSUFFICIENT_BALANCE`, 데드락 0건 |

### 왜 Redis가 아니라 MySQL에 저장했나
이체는 MySQL에 있다. 키를 Redis에 두면 "이체 완료"와 "키 저장"이 서로 다른 곳에서 일어난다.
- 이체는 끝났는데 Redis에 키를 저장하기 직전에 서버가 죽으면? 다시 요청이 왔을 때 키가 없으니 **이체가 두 번** 된다.
- MySQL에 두면 이체와 키가 **한 트랜잭션**이라 같이 저장되거나 같이 취소된다.

Redis가 더 빠르고 만료(TTL) 기능도 편하지만, 돈이 두 번 나가는 것을 막는 게 이 기능의 목적이라 MySQL을 골랐다.

### 처음 설계가 틀려서 바꾼 이야기
**처음 설계**: 이체 트랜잭션 안에서 키를 INSERT했다. 같은 키가 동시에 오면 두 번째 INSERT가 기다리다가 "중복"으로 실패하는 방식이다.

- 기본 테스트(첫 요청 성공)는 통과했다.
- 그런데 **첫 요청이 잔액 부족으로 실패하는 경우**를 테스트해 보니, 기다리던 요청 10건 중 5~8건이 **데드락**으로 실패했다.
- **비유**: 번호표 없이 문 앞에 10명이 몰려 있다가 문이 열리자 동시에 밀고 들어가려다 엉켜 버린 상황이다.

**바꾼 설계**: 먼저 키 행을 "PENDING"으로 **미리 만들어 두고**(번호표 기계를 먼저 세워 두기), 이체할 때는 그 행을 잠가서 한 명씩 처리한다.
- 이미 있는 행에 줄을 서는 건 단순한 줄서기라서 엉키지 않는다.
- 바꾼 뒤 3회 모두 10건 전부 정상 응답(`INSUFFICIENT_BALANCE`)이 나왔고, 데드락은 0건이었다.

### 그때 실행한 명령과 이유
| 명령 | 이유 |
|---|---|
| 실패 케이스 테스트를 일부러 추가 | 성공 케이스만 테스트하면 "첫 요청이 실패하면?"이라는 구멍을 못 본다. 실제로 여기서 문제가 나왔다 |
| `DROP TABLE idempotency_record` | 설계를 바꾸면서 상태 컬럼이 추가돼서, 테이블을 새로 만들게 했다. 이번 단계에서 새로 생긴 테이블이고 0건임을 확인한 뒤 지웠다 |
| `xargs -P 10`으로 curl 10개 동시 실행 | 테스트 코드뿐 아니라 실제 HTTP에서도 "1건 이체 + 9건 재전송"이 되는지 확인 |
| 빈 키를 `Idempotency-Key;` 문법으로 다시 보냄 | 처음엔 빈 키가 통과한 것처럼 보였다. 알고 보니 curl이 빈 헤더를 아예 안 보낸 것이었다. 실제로 빈 값을 보내면 400이 정상으로 나온다 |

### 아직 안 한 것
- 오래된 키 자동 삭제(만료)
- 사용자별로 키 나누기 (지금은 인증이 없어서 전체 공용)
- 같은 키로 요청이 대량으로 오면, 기다리는 동안 DB 커넥션을 차지한다

## 전체를 관통하는 원칙

1. **먼저 문제를 재현하고, 그다음 고친다.** 락 없이 → 문제 확인 → 비관적 락 → 데드락 확인 → 순서 고정. 매번 "고치기 전"과 "고친 후"를 숫자로 비교했다.
2. **테스트의 단언은 "올바른 결과"로 쓴다.** 고치기 전엔 실패하고, 고친 뒤엔 그대로 통과해야 한다.
3. **한 번 측정한 숫자는 믿지 않는다.** 재현 테스트는 2~3번, k6는 3번씩 돌렸다. 편차가 크면 "결론 낼 수 없음"이라고 적었다.
4. **실패 케이스도 테스트한다.** 6단계의 데드락은 "첫 요청이 실패하면?"을 테스트했기 때문에 발견했다.
