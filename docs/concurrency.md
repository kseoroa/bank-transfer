# 계좌 이체 동시성 문제와 해결: 비관적 락 vs 낙관적 락

> **테스트 환경**
> - Spring Boot 4.2, JPA(Hibernate), MySQL 8.0(InnoDB, 기본 격리 수준 REPEATABLE READ)
> - HikariCP 커넥션 풀 기본값 10, 테스트 스레드 32개, 로컬 WSL2 한 대에서 측정
>
> 아래 숫자는 모두 `TransferConcurrencyTest`, `TransferDeadlockTest`를 실제 MySQL에 돌려서 나온 값이다.
> 걸린 시간은 한 장비에서 잰 값이라 실행마다 편차가 있으므로 범위로 적었다.

---

## 1. 문제: 100건 이체했는데 10건만 반영됐다

**상황**: A 계좌(100,000원)에서 B 계좌로 1,000원씩 **100건을 동시에** 이체했다. 락은 쓰지 않았다.

| | 기대값 | 실제값 | 차이 |
|---|---:|---:|---:|
| A 잔액 | 0 | **90,000** | +90,000 |
| B 잔액 | 100,000 | **10,000** | −90,000 |
| A+B 합계 | 100,000 | 100,000 | 0 |

- 요청 100건 모두 **성공 응답**을 받았고 예외는 0건이었다. 그런데 실제로 반영된 건 10건뿐이다.
- 3번 실행해서 3번 모두 같은 결과가 나왔다. 걸린 시간은 1,087~1,158ms였다.
- **합계(100,000원)가 맞아서 총액 검증으로는 잡히지 않는다.** 에러 없이 사용자 90명의 이체가 사라졌다.

## 2. 원인: Lost Update

이체 한 건은 아래 SQL로 실행된다.

```sql
SELECT * FROM account WHERE account_number = 'A';   -- 락 없는 일반 조회
-- 자바 메모리에서 계산: 100,000 - 1,000 = 99,000
UPDATE account SET balance = 99000 WHERE id = 1;     -- 커밋 시점에 변경 감지(dirty checking)로 실행
```

UPDATE는 `balance = balance - 1000`이 아니라 **미리 계산해 둔 값(99000)** 을 그대로 쓴다.

| 시점 | 트랜잭션 1 | 트랜잭션 2 |
|---|---|---|
| t1 | SELECT → 100,000 | |
| t2 | | SELECT → 100,000 (1이 아직 커밋 전이라 같은 값) |
| t3 | UPDATE balance = 99,000 (행 락 획득) | |
| t4 | | UPDATE 시도 → 락 대기 |
| t5 | COMMIT (락 해제) | |
| t6 | | 대기 끝 → UPDATE balance = 99,000 → COMMIT |

두 건이 성공했는데 잔액은 1,000원만 줄었다. 트랜잭션 1의 변경이 덮어써져 사라졌다.

- **REPEATABLE READ가 막지 못하는 이유**: REPEATABLE READ는 "내 트랜잭션 안에서는 같은 값을 다시 읽는다"는 보장이다. "내가 읽은 값을 남이 못 바꾼다"는 보장이 아니다. 일반 SELECT는 MVCC 스냅샷을 읽을 뿐 락을 걸지 않는다.
- **UPDATE의 행 락으로도 부족한 이유**: 행 락은 쓰기 순서만 정해 줄 뿐이다. 두 번째 트랜잭션은 기다린 뒤에도 오래된 값으로 계산한 결과를 그대로 쓴다.
- **정확히 10건인 이유**: 한 번에 최대 10개(커넥션 풀 크기) 트랜잭션이 같은 값을 읽고, 모두 같은 값을 쓴다. 결국 10개가 1건으로 합쳐져 100건이 10건이 된다. 커넥션 풀을 5로 줄여 다시 돌리면 **A 80,000원 / B 20,000원**(20건 반영)으로 바뀐다.

## 3. 해결 1: 비관적 락 (`SELECT ... FOR UPDATE`)

읽을 때부터 행을 잠가서, 다른 트랜잭션은 같은 행을 읽기 전에 기다리게 한다.

```java
// AccountRepository
@Lock(LockModeType.PESSIMISTIC_WRITE)   // MySQL: SELECT ... FOR UPDATE
@Query("select a from Account a where a.id = :id")
Optional<Account> findByIdForUpdate(@Param("id") Long id);
```

### 데드락: A→B와 B→A가 동시에 일어날 때

처음에는 "보내는 계좌 → 받는 계좌" 순서로 락을 걸었다. 그러자 T1(A→B)은 A를 잠그고 B를 기다리고, T2(B→A)는 B를 잠그고 A를 기다리는 **순환 대기(데드락)** 가 생겼다.

**테스트**: A와 B 모두 100,000원으로 시작해서 A→B 50건과 B→A 50건을 동시에 실행했다.

| 락 순서 | 성공 / 실패 | A / B 잔액 (기대 100,000 / 100,000) | 걸린 시간 |
|---|---|---|---|
| 보내는 계좌부터 (1회) | 49 / **51** `CannotAcquireLockException` | 99,000 / 101,000 | 1,471ms |
| 보내는 계좌부터 (2회) | 50 / **50** | 102,000 / 98,000 | 1,624ms |
| **id 오름차순** (3회) | **100 / 0** (3회 모두) | 100,000 / 100,000 | 1,502~3,615ms |

InnoDB가 데드락을 감지해 한쪽을 롤백하기 때문에 멈추지는 않았다. 하지만 양방향 이체의 절반 정도가 실패했다.

### 해결: 이체 방향과 상관없이 항상 id가 작은 계좌부터 락

```java
@Transactional
public TransferResult transfer(String fromAccountNumber, String toAccountNumber, long amount, ...) {
    Long fromId = findAccountId(fromAccountNumber);   // id만 조회 (락 없음)
    Long toId = findAccountId(toAccountNumber);

    Account from, to;
    if (fromId < toId) { from = lockAccount(fromId); to = lockAccount(toId); }
    else               { to = lockAccount(toId);     from = lockAccount(fromId); }

    from.withdraw(amount);
    to.deposit(amount);       // save() 없이 변경 감지로 UPDATE
    ...
}
```

- 모든 트랜잭션이 같은 순서로 락을 잡으므로, 대기가 순환으로 이어지지 않는다.
- 단위 테스트(`InOrder`)로 "B→A 이체도 id 1 → 2 순서로 락을 건다"는 규칙을 고정했다.
- **id만 먼저 조회하는 이유(설계 판단)**: 처음에 엔티티 전체를 읽으면 오래된 잔액이 영속성 컨텍스트에 남는다. 그 뒤 `FOR UPDATE`로 최신 행을 읽어도 Hibernate는 이미 관리 중인 엔티티를 그대로 돌려준다. 그러면 락은 걸었는데 오래된 잔액으로 계산하는 lost update가 다시 생긴다. 그래서 id만 projection으로 가져온다.

## 4. 해결 2: 낙관적 락 (`@Version` + 재시도)

락 없이 읽고, 커밋할 때 다른 트랜잭션이 먼저 바꿨는지 version으로 확인한다.

```java
// Account
@Version
private long version;   // UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?
```

내가 읽은 뒤 누군가 먼저 커밋했다면 version이 달라서 갱신된 행이 0건이 된다. 이때 `OptimisticLockingFailureException`이 발생한다.

### 재시도 방식

```java
for (int attempt = 1; attempt <= maxAttempts; attempt++) {          // 기본 5번
    try {
        return transactionTemplate.execute(status -> transferOnce(...));   // 시도마다 새 트랜잭션
    } catch (OptimisticLockingFailureException e) {
        if (attempt == maxAttempts) break;
        sleepWithJitter();                                            // 20~40ms 무작위 대기
    }
}
throw new BusinessException(ErrorCode.TRANSFER_CONFLICT);           // 409
```

- **시도마다 새 트랜잭션을 연다.** 같은 트랜잭션 안에서 재시도하면 영속성 컨텍스트에 오래된 엔티티가 남아 계속 충돌한다. 그래서 `@Transactional` 대신 `TransactionTemplate`을 썼다. 같은 클래스의 `@Transactional` 메서드를 자기 자신이 호출하면 프록시를 거치지 않는 문제(self-invocation)도 이 방식으로 피했다.
- **version 충돌만 재시도한다.** 잔액 부족 같은 비즈니스 예외는 다시 해도 결과가 같으므로 바로 실패로 돌려준다.
- **무작위 대기(jitter)를 둔다.** 충돌한 요청들이 똑같이 기다렸다 다시 들어오면 또 함께 충돌한다.
- **양방향 데드락 대비**: 낙관적 락 경로는 `FOR UPDATE`를 쓰지 않지만, 커밋할 때 UPDATE가 행 락을 잡는다. 그래서 `hibernate.order_updates: true`로 UPDATE를 PK 순으로 정렬했다. 양방향 테스트(A→B 50 + B→A 50)에서 데드락은 0건이었다. 이 옵션을 끈 상태는 측정하지 않았다.

## 5. 비교 (1번과 같은 조건: A 100,000원 → B, 1,000원 × 100건 동시)

| 방식 | 성공 | 실패 | 재시도 | 최종 잔액 A / B | 정합성 | 걸린 시간 |
|---|---:|---:|---:|---|---|---|
| 락 없음 (2단계) | 100 | 0 | — | 90,000 / 10,000 | ❌ 90건 유실 | 1,087~1,158ms (3회) |
| **비관적 락** | **100** | **0** | 0 | **0 / 100,000** | ✅ | 1,677~1,805ms (3회) |
| 낙관적 락 (최대 5번 시도) | 44~45 | 55~56 | 308~313 | 55,000~56,000 / 44,000~45,000 | ✅ 성공 건수만큼 정확히 이동 | 1,361~1,450ms (3회) |
| 낙관적 락 (최대 30번) | 99 | 1 | 786 | 1,000 / 99,000 | ✅ | 2,838ms (1회) |
| 낙관적 락 (최대 100번) | 100 | 0 | 800 | 0 / 100,000 | ✅ | 3,290ms (1회) |

- 비관적 락과 낙관적 락은 같은 코드(두 방식을 함께 둔 4단계 코드)에서 연달아 측정했다. 락 없음은 2단계 코드에서 따로 측정한 값이다.
- 낙관적 락의 "실패"는 돈이 사라진 게 아니라 `TRANSFER_CONFLICT`(409)로 **이체가 거절된 것**이다. 성공한 이체는 하나도 유실되지 않았다.
- 낙관적 락(5번)이 더 빨라 보이는 이유는 절반 넘게 일찍 포기했기 때문이다. 100건을 모두 성공시키려면(100번) 재시도가 800번 필요했고, 비관적 락보다 약 2배 오래 걸렸다.

## 6. 결론: 이체에는 비관적 락

1. **이체는 같은 계좌에 요청이 몰리는 일이 흔하다.** 이 테스트처럼 한 행에 충돌이 집중되면, 커넥션 10개 중 한 번에 하나만 커밋에 성공하고 나머지는 모두 충돌한다. 낙관적 락은 "충돌은 드물다"를 전제로 한 방식인데, 그 전제가 맞지 않는다.
2. **낙관적 락은 버려지는 작업이 많다.** 100건을 성공시키는 데 재시도 800번이 들었다. 한 번 실패한 시도마다 SELECT, UPDATE, 롤백을 하고 그동안 커넥션도 붙잡는다. 비관적 락은 기다릴 뿐 같은 일을 다시 하지 않는다.
3. **재시도 횟수를 정하기 어렵다.** 적게 잡으면 정상 이체가 절반 넘게 실패하고(5번: 55~56건 실패), 많이 잡으면 비관적 락보다 느리다(100번: 3,290ms). 이체 실패는 사용자가 직접 다시 해야 하므로 금융 서비스에서 받아들이기 어렵다.

비관적 락을 쓸 때는 **락 순서 고정(id 오름차순)** 을 함께 적용해야 양방향 이체의 데드락을 막을 수 있다.

> 낙관적 락은 서로 다른 행을 고치는 일이 대부분이라 충돌이 드문 작업(예: 프로필 수정)에 맞는다.
> 이 문서의 측정은 "한 계좌에 몰리는 경우"뿐이다. 충돌이 드문 경우의 비교는 k6 부하 테스트(`k6/README.md`)에서 따로 다뤘다.

## 7. 면접 예상 질문

**Q1. MySQL 기본 격리 수준이 REPEATABLE READ인데 왜 lost update가 생겼나요?**
REPEATABLE READ는 내 트랜잭션 안에서 같은 값을 다시 읽는다는 보장일 뿐, 남이 그 값을 바꾸지 못하게 막지는 않습니다. 일반 SELECT는 락 없이 스냅샷을 읽으므로 여러 트랜잭션이 같은 잔액을 동시에 읽습니다. 그리고 JPA는 메모리에서 계산한 값을 `SET balance = 99000`처럼 그대로 쓰기 때문에, 나중에 커밋한 쪽이 앞선 변경을 덮어씁니다.

**Q2. 100건 중 정확히 10건만 반영된 이유는요?**
커넥션 풀 크기가 10이라 한 번에 최대 10개 트랜잭션이 같은 값을 읽고 같은 값을 씁니다. 그래서 10개가 1건으로 합쳐집니다. 풀을 5로 줄였더니 20건이 반영되는 것으로 확인했습니다. 즉 피해 규모가 동시 요청 수와 설정에 따라 달라지기 때문에, 테스트 환경에서는 잘 안 보이다가 트래픽이 몰릴 때 터지는 유형의 버그입니다.

**Q3. 비관적 락에서 데드락은 어떻게 막았나요?**
A→B와 B→A를 동시에 실행하니 100건 중 약 50건이 데드락으로 실패했습니다. 그래서 이체 방향과 상관없이 항상 계좌 id가 작은 쪽부터 락을 걸도록 바꿨고, 이후 3회 모두 100건이 성공했습니다. 이때 id는 엔티티가 아니라 id만 먼저 조회합니다. 엔티티를 미리 읽으면 오래된 잔액이 영속성 컨텍스트에 남고, 이후 `FOR UPDATE` 결과가 반영되지 않기 때문입니다.

**Q4. 낙관적 락 재시도를 구현할 때 주의한 점은요?**
세 가지입니다. 첫째, 시도마다 **새 트랜잭션**을 열었습니다. 같은 트랜잭션 안에서 재시도하면 오래된 엔티티 때문에 계속 충돌하고, 같은 클래스의 `@Transactional` 메서드를 직접 호출하면 프록시가 적용되지 않아서 `TransactionTemplate`을 썼습니다. 둘째, **version 충돌만** 재시도하고 잔액 부족 같은 비즈니스 예외는 바로 실패시켰습니다. 셋째, 재시도 전에 **무작위 대기(jitter)** 를 둬서 충돌한 요청들이 동시에 다시 몰리지 않게 했습니다.

**Q5. 이체에 비관적 락을 고른 이유와, 낙관적 락은 언제 쓰나요?**
같은 계좌에 이체가 몰리는 조건에서 낙관적 락은 재시도 5번 설정 기준으로 100건 중 55~56건이 실패했습니다. 전부 성공시키려면 재시도가 800번 필요했고 시간도 비관적 락(1.7~1.8초)의 약 2배(3.3초)였습니다. 비관적 락은 100건을 모두 실패 없이 처리했습니다. 낙관적 락은 충돌이 드물고 실패 시 재시도 비용이 작은 작업에 맞습니다. 비관적 락은 락을 기다리는 동안 커넥션을 붙잡기 때문에, 요청이 극단적으로 몰리는 계좌에서는 커넥션 풀이 바닥날 수 있다는 점도 알고 있어야 합니다.
